**标准开发流程**：需求分析 → 方案设计 → 构建 → 测试 → 上线。前两个阶段为对话式推进（产物：`.agent/spec.md` 需求规格说明书、`.agent/plan.md` 设计说明书），阶段结束由用户主动宣布；本文件约束构建及之后的执行。

## 1. 工作流约束（强制）

1. **按需恢复上下文**：新会话先读取 `.agent/status.md` 的「当前状态」；按当前任务编号读取其任务条目，按需检索 `spec.md`、`plan.md` 和 `history.md` 的相关段落，不默认全文读取。摘要仅作导航；缺失、过期或与原文/代码冲突时核对相关记录、Git 和代码后更新状态。
2. **权威来源**：需求和验收标准以 `spec.md` 为准；当前设计和现行决策以 `plan.md` 为准；任务清单及当前状态见 `status.md`；过程、验证及决策历史见 `history.md`。来源冲突时查证，不凭摘要覆盖原文。
3. **按清单执行**：`status.md` 的任务清单须经用户确认，严格按顺序、不跳依赖，一次只实现一个任务，不超前实现。
4. **完成即记录和验证**：实现后运行合适的验证，将任务记为「已实现待验收」（仍为 `[ ]`），更新当前状态，在 `history.md` 追加任务、文件、验证结果和问题；单独提交本任务，告诉用户如何验证并等待确认。用户确认后才标记 `[x]`、同步当前状态并记录验收，另行提交验收记录（`docs: T0XX 验收记录`）；未确认前不开始下一个任务。
5. **决策留痕**：需决策的技术选型先记录 D0XX 背景、选项、理由和代价，再继续；现行结论与编号写入 `plan.md`，详细过程追加到 `history.md`。
6. **保留历史**：`history.md` 只追加、不删除或改写旧记录；被替代决策用新记录指明旧编号，当前设计只保留现行结论。
7. **需求变更走修订**：先修改 `spec.md`，追加变更记录、标待确认；列出影响并同步 `plan.md` 和 `status.md` 的任务，受影响的已完成任务按需回退并在 `history.md` 记录。用户确认后才改代码。
8. **设计变动先算账**：技术栈、数据模型、模块结构、关键接口或依赖的调整，先在对话中分析收益、风险、影响范围和迁移成本；经用户主动确认后修改 `plan.md`，在 `history.md` 追加决策，并同步受影响任务与状态。修改完成后提交用户审阅，确认后再继续实现。
9. **回退与交付**：回退前先检查工作区、提交历史和受影响范围，优先针对性修复或 `git revert`；涉及丢弃修改或改写历史须事先获得用户明确授权。最终验证按项目需求、异常与实际测试方式进行；推送、发布和部署按用户授权及项目环境处理，不假定存在特定 CI 或远端。

## 3. 代码约定

- 所有函数加类型注解
- API 路由使用 RESTful 命名（复数名词）
- 配置通过环境变量读取，不硬编码
- 每个模块有清晰的单一职责
- 错误处理只在系统边界（用户输入、外部 API），内部代码信任框架 guarantee

## 4. Git 规范

- 每个任务一个 commit：`feat: T0XX [任务简述]`
- 修复 commit：`fix: T0XX [问题描述]`
- 文档 commit：`docs: [内容]`
- 不使用 `--no-verify` 跳过 hook
- 不使用 `git add -A`，按文件添加

## 5. 文件结构约定

```
.agent/          ← 项目状态（Agent 读写，不删除）
  spec.md        ← Phase 1: 需求规格说明书（需求分析产物）
  plan.md        ← Phase 2: 设计说明书（方案设计产物）
  status.md      ← 当前状态、任务清单及待验收事项
  history.md     ← 只追加的任务、验证、决策与变更历史
src/             ← 实际代码
tests/           ← 测试代码
```
